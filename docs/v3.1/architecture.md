# Ferry Plus 3.1 技术方案

状态：19项代码优化、整体技术审查、有限真实App回归及本地候选交付已完成；实际验证见 [实施记录](implementation.md)。日期：2026-10-25。产品输入为 [3.1 优化方案](features.md) V31-F01～V31-F19。实施基线为 `7e37e7f`，与3.0发布二进制的业务源码 `64aa672` 一致；当前有效实现及提交见 [实施记录](implementation.md)。

## 1. 技术结论与现状

沿用 SwiftUI、FerryCore、BaiduKit、QuarkKit 和 DownloadKit。优化落在既有职责内：消除重复工作、用完整上下文替代并列字段、统一已经等价的公共步骤，不新增通用工作流框架、数据库或第二套传输状态。

3.0基线中确认的优化动因：

- `MainView.body` 和 `transferScope` 分别取得 `visibleItems`，侧栏又取筛选结果；渲染存在重复计算。异步命令另行核对当前范围是正确边界，必须保留。
- UploadView 的已加载账号／会话／目录、AppModel 的上传草稿，以及三个页面的导出／删除／校验选择，有成组变化的分散状态。
- UploadEnvironment 同时保存普通建目录闭包和可选的检查点闭包。仓库正式构造方为百度、夸克两个工厂；两者已经提供后者。
- 正常百度覆盖链为 Coordinator 校验暂存 → Publisher 再读暂存 → Publisher 核对发布后文件 → Coordinator 再核对最终文件；同一新内容读取四遍。旧内容及快照的读取另有职责，不能算入可直接删除的重复项。
- `replacementCheckpoint` 多次保存相同旧版本记录；`received` 读取文件后，`saveFile` 为计算差值又读取一次。
- 两种完成通知重复授权／发送步骤；Keychain 同时存在 checked 和吞错包装；版本信息和打包校验也有多处来源。
- 无 `.codegraph/`，本次直接核对源码。基线动因不替代实施验证；以下职责描述当前实现，逐项证据及真实App未完成项单列。

主要入口：[MainView](../../BaiduPCS-Swift/MainView.swift)、[UploadView](../../BaiduPCS-Swift/UploadView.swift)、[AppModel](../../BaiduPCS-Swift/AppModel.swift)、[UploadCoordinator](../../Packages/FerryKit/Sources/FerryCore/UploadCoordinator.swift)、[Publisher](../../Packages/FerryKit/Sources/FerryCore/UploadReplacementPublisher.swift)。

## 2. 职责与状态所有权

| 所有者 | 继续负责 | 本次收敛方式 |
| --- | --- | --- |
| MainView／具体页面 | 当前筛选、选择、展示和用户确认 | 渲染复用局部计算结果；每个交互流程拥有一个明确状态 |
| AppModel | 当前账号／客户端、入口草稿、传输装配、系统通知 | 草稿合为值对象；通知发送共用一个私有入口，不新增镜像账号状态 |
| UploadCoordinator | 调度、阶段转换、持久化顺序、完成判定 | 消费真实校验结果；只有满足旧值有效条件才减少读取 |
| UploadReplacementPublisher | 快照、claim、禁止重名覆盖发布、准确结果核对 | 返回本次实际读取产生的校验结果，不只返回发布状态 |
| UploadStore／IntegrityStore | 磁盘格式、原子写、记录校验 | 共享读取基础；相同证明可省重复写，失败仍可恢复归档 |
| 网盘适配器 | 请求协议、会话检查、准确回执 | 统一建目录回调契约，保留网盘差异和确定未发送分类 |
| 构建脚本／CI | 产品版本、签名核对、交付包 | 单一产品版本来源和打包入口；签名身份不随优化变化 |

## 3. 功能技术映射

| 功能 | 行为与技术落点 | 数据／接口 | 主要边界与验证 |
| --- | --- | --- | --- |
| F01 主列表计算 | MainView 一次渲染生成过滤结果、排序列表和选择范围 | 局部只读投影；不增加 `@State` 缓存 | 筛选组合结果相同；命令跨 await 后仍重新取当前范围 |
| F02 上传上下文 | UploadView 用一个可选 LoadedDirectoryContext 同时保存账号、客户端身份、目录及列表 | UI 内存值；请求代次继续保留 | Tab／账号／会话变化同时失效，迟到结果不覆盖新页 |
| F03 上传草稿 | AppModel 用 UploadDraft 包含 provider、directory、files | 保持原 sheet 路由，入口一次写入 | 主窗／目录行／菜单来源一致；取消后旧草稿不污染下一次 |
| F04 移除流程 | MainView 用明确阶段驱动确认、导出和移除 | 页面私有状态；Core 删除契约不变 | 原确认文案、依据保留、取消、部分失败及可见范围不变 |
| F05 校验选择 | NetdiskDownloadView 按选择模式持有对应草稿 | 单独关联手填值、候选或导入清单 | 保留原切换时的保留／清空规则；不自动选用旧摘要 |
| F06 明细辅助流程 | UploadFilesView 导出、重定位、定位结果各自成组 | 各流程私有状态，分页不变 | 各流程可并行的原能力不被一个全局 busy 意外串行化 |
| F07 格式化 | Formatting复用上传容量/速度的相同表达式，保留既有时间格式差异 | 只读展示，不改数值来源 | 0值、无速度、无预计时间和本地化样例保持约定口径 |
| F08 建目录 | UploadEnvironment 仅一个必需的带回执闭包 | 普通 makeDirectory 通过空回调调用同一实现 | 回执先保存，后置检查后发生错误不能丢回执 |
| F09 覆盖回读 | Publisher 生成真实验证记录，Coordinator 共用完成收尾 | 发布状态＋可核对的本次最终 IntegrityRecord | 每次取消／恢复／冲突的读取目的先证明；不能盲减到两次 |
| F10 归档去重 | 旧版本证明不变时不重复原子写 | 稳定 record ID、准确引用、摘要、原名、实际校验时间 | 缺失或写失败须补归档；真实新回读更新时间，后续阶段不造时间 |
| F11 检查点读取 | 有可靠旧值时传递旧摘要计算差值 | 内存上下文，不修改 JSON 版本 | actor 重入、晚到回执或外部入口可能改值时继续重读 |
| F12 记录扫描 | IntegrityStore 共享 JSON 枚举／解码／验证基础 | 不改 matching／candidates／inventory 对外结果 | 查询遇坏记录报错；inventory逐项报告，不能统一吞错 |
| F13 通知 | AppModel 统一发送，调用方分别生成内容 | 请求ID、内容和授权Task仍沿用 | 原授权次数、完成时机、通知内容及关闭收尾一致 |
| F14 凭据IO | KeychainItem 以 checked 操作为内部基础 | 不改 service／account 键；调用层显式处理结果 | 接口收敛与可见错误变化分开，见第6节 |
| F15 无用属性 | 删除无人引用的 canDownloadFromNetdisk | 无外部接口迁移 | 全库／调试入口复查引用，功能入口仍可用 |
| F16 根目录规则 | Provider.rootReference集中定义 | 百度 `/`、fsID=0；夸克 fid=`0` | 不能混用当前目录，根目录删除限制保留 |
| F17 验证输出 | AppDelegate 验证分支共用编码／输出小方法 | 现有参数、JSON字段、退出码和shutdown顺序 | DEBUG隔离不变；文档所列Release会话探针继续可用 |
| F18 版本来源 | 新增单一产品版本配置，供脚本和Xcode读取 | `Config/Version.xcconfig` | 缺失即失败；tag与产品版本一致，CI构建号仍可单独覆盖 |
| F19 打包复用 | CI调用现有 Scripts/package-app.sh | 输出ZIP及SHA文件，CI适配实际输出路径 | App名称、arm64、签名、根目录和摘要与原产物合同一致 |

完整编号前缀为 `V31-`，上表 F01 对应 V31-F01，依此类推。候选只按已有调用点迁移，不为尚无调用方的扩展设计接口。

## 4. 界面收敛设计

### 4.1 渲染投影与实时命令分开

一次 body 求值中计算过滤后的上传／下载集合、排序后的 visibleItems 和选中项；把该局部结果传入 scope 与子视图。侧栏仍不预先套用当前分类，保证分类计数含义不变。不通过跨渲染缓存跳过源数据、查询或分类变化。

`perform`、移除确认后的操作及跨 await 的逐项命令继续重新核对当前可见范围和动作资格。渲染结果复用不能变成“冻结旧列表后一直执行”。

### 4.2 值对象与流程阶段

LoadedDirectoryContext 和 UploadDraft 是各自单一所有者下的值对象，不能变成另一个账号服务。LoadRequest、PreflightRequest、Creation、Submission 的账号／会话快照和代次仍承担迟到回调校验职责，不因字段合并删除这些身份信息。

移除流程使用 idle（空闲）、processing（处理中）、awaitingDecision（等待保留依据决定）、exporting（导出清单）四阶段；流程持有队列及错误，阶段持有当前请求及导出文档。原本允许的独立操作仍独立，错误汇总交回主窗口。文件导出取消和导出失败分别沿用原策略，不借重构改变清理行为。

校验模式与其草稿关联，必须先记录原实现切换时哪些值保留、哪些清空，再迁移；不能一律在切换时清空来换取代码简短。UI状态全部为内存状态，不落盘、不改变任务JSON。

## 5. 覆盖回读与持久化优化

### 5.1 先证明，再去重

先为正常发布、发布回执丢失后的查询、已发布恢复、取消和冲突画出实际调用序列，标出每次读取的准确对象、期望SHA、阶段和必要性。正常路径的新内容四次回读是静态调用链事实，不代表任意恢复路径都能直接删掉两次。

UploadReplacementResult包含发布状态和本次调用实际产生的最终 IntegrityRecord；只有真实完整回读成功才有成功记录。Coordinator 将“读取并验证”与“保存已验证结果、更新文件完成状态、释放准备授权”分开，共用收尾。保存之前核对账号、准确对象、长度、摘要、uploadFileID及验证状态，不复制一个历史成功布尔值冒充新证明。

正常路径由 Publisher 执行暂存验证与最终验证，Coordinator消费最终记录，新内容完整读取从四次减少到两次；旧字节、独立快照、claim及原名保护不删。跨进程恢复仍重新核对对象并完整回读，不复用上一进程的内存证明。阶段进度必须来自实际读取，发送100%与最终完成仍分开。

去重目标只统计新内容回读。旧内容基准、备份快照、失败重试与其他读取单独计数；不据此宣称整体流量减半。若某次读取承担独立必要条件或无法可靠传递结果，保留该次读取并记录结论。

### 5.2 旧版本归档

省写的条件是同一稳定ID对应的账号、准确引用、原始摘要、长度、原文件名和实际校验时间都相同；不是仅比较ID存在。未知版本、读取错误和记录损坏不能当成“已归档”。文件检查点已保存而归档失败时，后续恢复仍补齐独立记录；任务移除后旧版本依据仍保留。保持文件先写、归档随后写的失败语义。最终完成前也通过同一归档方法补齐旧依据，避免published检查点落盘后归档失败、真实重试绕过检查点而丢失独立记录；缺实际校验时间的旧格式不伪造依据。不增加跨文件事务。

### 5.3 文件旧值复用与扫描

仅received复用刚读取文件的confirmedBytes与phase两字段摘要；引擎父任务逐个await回执，停止/重定位等等待worker收尾，其余52处saveFile调用仍重读。只有能证明来自同一文件写入上下文、期间没有其他写入者的旧摘要才可复用；验证范围包括 actor 在 store await 期间的重入、取消等待、晚到成功回执、核对和显式重试。无法证明时保留重读，不为省一次IO新增持久版本字段、通用锁或镜像缓存。

分片回执持久化和已确认位移不降低频率，不把检查点攒到末尾写。`saveFile` 只有真实 worker 推进批次阶段的规则继续保留。

IntegrityStore 先只共享枚举、读取和记录校验。matching、candidates仍遇坏记录抛错，inventory仍逐项记录失败；不让一种容错策略覆盖所有用途。本版不引入全库常驻缓存、索引数据库或新存储格式；是否需要索引须有后续规模证据。

## 6. 通知、凭据与工程入口

- 通知统一私有发送入口，调用方生成 title、body 和稳定请求ID。保留授权等待、后续系统权限重查、取消、退出与静默通知失败的原策略；不新增通知队列和重试后台服务。
- 凭据IO内部收敛到明确错误契约，但当前百度与代理的部分吞错行为和夸克抛错行为不相同。首先列行为对照：未保存、拒绝读取、损坏数据、删除失败。单纯统一接口不授权改变可见错误策略；若需要新增弹窗或将原降级改为启动失败，该子项须标为行为修正并单独决定，3.1默认保留原外部约定，不混入等价重构。不能以空值掩盖新的必需边界错误，也不增加一组未说明的默认回退。
- F17仅复用编码和报告输出等确实相同的步骤；不同验证命令的退出条件、信号取消与shutdown先后不机械统一。大部分代码已经在DEBUG内，维护收益与Release包体收益分别说明。文档里的 `--verify-quark-session` 不能直接删除或改为仅Debug。
- F18使用 `Config/Version.xcconfig` 定义 MARKETING_VERSION，两种Xcode配置引用它；本机构建脚本严格读取同一值，去掉工程中重复硬编码。CI核对tag版本再构建，Xcode在Sources前通过同一读取脚本比对实际MARKETING_VERSION，缺值或外部覆盖不一致明确失败；CURRENT_PROJECT_VERSION保留原构建号来源。正式产品版本只在候选完成时更新为3.1，不能改已发布3.0标签。
- F19复用打包脚本，不强行合并本机CLT和CI的Xcode构建方式；CI取脚本实际输出的ZIP／SHA路径。实际GitHub运行与本地配置合同验证分别记录，本轮本地实施不触发发布工作流。

## 7. 兼容、回退与验证

- 使用3.0任务／设置／校验记录副本验证3.1读取和保存后仍可由3.0读取；包含已完成、暂停、待核对和旧可选字段缺失记录。保持ID、源引用、位移及摘要，不删除原始数据。未证明兼容时不修改真实用户数据。
- 每个候选先检查全部调用方，替代实现与迁移验证完成后才删旧入口；最终没有本次遗留双实现或废弃兼容分支。逐项本地提交代码和直接文档，失败可独立回退；已公开提交用正常回退提交，不强推。
- 现有测试按改动模块选择，公共Core／接口变化编译相关target并运行已有相关套件。无明确要求不新增测试类；必要的临时故障验证放隔离scratch，标注真实源码、替身与证据范围。
- App与包测试不共享异版本SDK的构建输出；统一App构建前冻结源码，避免并发修改输入。沿用无需完整Xcode的本地CLT构建路径，实际SDK以运行时本机可用版本核实。
- 最终Review核对功能、状态所有权、异常语义和本次清理；重新构建固定签名arm64 Release App，Agent实际操作两家正常传输、覆盖、校验、删除及确认取消，真实内容用小样本全SHA比对。测试对象可准确归属，清理只移入废纸篓／网盘回收站。
- 聚焦检查Task收尾、订阅释放、许可归零、无重复worker和意外自重试；不恢复已取消的整套资源专项或睡眠矩阵，不重新等待多GiB传完。
- 最后核对App版本、标识、签名、ZIP解包和SHA，记录优化前后调用／IO计数及保留项。没有相关证据时不声称功能绝对不受影响。

## 8. 实施时的验证入口

以下是实施入口，实际执行命令、源码冻结范围及结果以实施记录为准。先核实本机工具链及SDK，沿用仓库脚本默认的本机App SDK；包测试若使用不同SDK，必须使用独立scratch。历史测试数量不作为3.1通过条件。

```sh
# 受影响的现有包测试；按实际可用SDK选择FERRY_MACOS_SDK。
env FERRY_MACOS_SDK=macosx bash Scripts/test-packages.sh \
  --configuration release --scratch-path "$PWD/.build/package-tests-v31"

# 源码冻结、候选版本设为3.1后，重建并打开实际App。
env FERRY_BUILD_CONFIGURATION=release bash Scripts/build-app.sh
open ".build/Ferry Plus.app"

# 实际验收通过后才打包；确认产物版本为3.1，不能拿旧3.0冒充。
bash Scripts/package-app.sh
```

固定证书不可用或签名身份与3.0不一致时，不能把脚本的临时签名回退当成验收通过；先定位本机构建条件，不能通过更换应用标识／删除凭据来避开授权问题。现有3.0App与ZIP先保留，实际验收默认运行构建目录中的候选，不自动替换“应用程序”里的稳定版。

### 系统面板的取消与归属

文件导入／导出取消使用各自的onCancellation，不能假定取消会调用onCompletion；presentation先关闭时保留请求及文档，直到所属完成／取消回调才释放。选源面板也持有独立请求UUID，同一文件两代选择不能共用身份。上传文件选择使用实际上传页窗口的附着面板，所属窗口由WindowReader回填到presenter的弱引用，避免独立模态窗口脱离页面及新增窗口强持有。
