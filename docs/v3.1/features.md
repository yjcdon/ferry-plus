# Ferry Plus 3.1 优化方案与功能清单

状态：19项代码优化、技术Review、真实App回归及交付已完成；按用户后续明确指令发布 [3.1](https://github.com/yjcdon/ferry-plus/releases/tag/v3.1) 并更新本机App，实际结果见 [实施记录](implementation.md)。日期：2026-10-25。基线：已发布 [3.0](https://github.com/yjcdon/ferry-plus/releases/tag/v3.0)，实施基线 `7e37e7f`，业务源码 `64aa672`。技术设计见 [架构设计](architecture.md)，设计完成后拆解的工作见 [任务清单](tasks.md)。

## 1. 定义、目的与方法

这是 3.0 的优化子方案。对象是现有 SwiftUI 界面、本地 Swift 传输核心和构建发布流程。用户继续使用百度、夸克的上传、下载、目录管理及校验功能，不学习新流程。

目的：在保持既有功能、交互和数据兼容的前提下，减少重复处理及维护成本。先做边界明确的小改动，再收敛界面状态，最后评估回读与持久化优化；每项先建立行为基线，实施后证明行为等价，不能把“代码减少”当作验收。

本方案输入来自本次源码审查的 19 项候选及用户关于不影响现有功能的要求。19 项逐项评估，不承诺全部都应该修改；无法证明等价、收益不成立的项目保留原实现，明确记录原因，不以新增抽象凑优化项。

## 2. 继承范围与边界

- 保留两家官方网页登录、既有 Keychain 凭据、账号隔离、文件／文件夹上传、正常续传、完整 SHA-256 回读、下载校验、网盘删除及百度安全覆盖，详见 [3.0 功能](../v3/features.md)。
- 极端未知提交全自动恢复、过期会话自动重建、远端分片立即取消和夸克安全覆盖继续延期，不因优化顺手扩展。
- 不更换语言、UI 框架、存储介质或轻量策略；不强行合并上传、下载两套不同协议流程。
- 不改变应用标识、Keychain 条目名、固定签名身份、任务及校验 JSON 格式。版本号更新到 3.1 是交付元数据变化，不代表先完成业务优化。
- 延续此前取消生命周期和最终资源专项的决定，不重新开展睡眠唤醒矩阵或多 GiB 长时间验证。只针对实际优化核对调用次数、读写次数及必要资源释放，不承诺未经测量的 CPU、内存、包体降幅。
- 当前已获实施授权：逐项本地提交、最终Review、重新构建App并由Agent通过Computer Use验证；发布按届时3.1的明确指令执行，不沿用3.0的发布动作。

## 4. 必须保持的业务规则

1. 拖入只选择文件；网盘、账号和目标目录确认后才上传。取消、切 Tab 或换会话不能让旧确认继续提交。
2. 批量操作只作用于执行时仍可见、仍符合条件的任务；不能把渲染时的列表缓存用于异步操作的权限范围。
3. 准确回执先持久化，再进行可能失败的后置检查；真正发出请求后的错误仍可能代表结果未知。
4. 发送字节到 100% 不等于完成；完整摘要校验及必要发布完成后才能显示成功。未知摘要仍明确未验证。
5. 百度覆盖保留独立旧版本、冲突保护和最终对象核对。不能因减少回读而取消某个必需阶段的证明。
6. 已确认无需本地字节时可继续远端恢复；仍有缺片或需重新分块时，原授权和源版本检查继续生效。
7. 移除任务、删除网盘文件、清理校验依据是不同操作，保留各自确认、保留数据和失败处理规则。

## 5. 验收口径

- 每项有实施前行为、修改内容、实施后证据和结果；状态区分“已实现并验证”“保留原实现”“延期”，不把静态审查写为通过。
- 正常功能与上列规则保持一致。若某项必须改变用户可见行为，先记录具体差异，该子项不以等价重构名义直接实施。
- 重复计算、回读或写入优化用对应操作计数证明；收益按实际场景说明，不把新文件回读减少等同整体流量减半。
- 最终使用固定签名的 arm64 Release App，复用已有登录，实际操作上传、下载、覆盖、删除、筛选及确认／取消流程；记录与模拟验证的范围分开。
- 不因单项优化未成立重启已停止的超大文件测试或长期接口探索。维持可用的 3.0，候选改动能逐项回退。
